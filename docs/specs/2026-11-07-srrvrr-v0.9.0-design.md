## Goals

Three questions about the server's file shares, of equal weight:
- **Why is it slow?** Every 5 seconds, name the server resource closest to its limit (the network link, the drive
  behind the share, or the CPU), or say it's not the server, with the numbers behind it.
- **What's happening?** Every PC connected to the shares, how fast it's reading and writing, and in which folders:
  folders and counts, never file names. PCs the owner named in the config get their friendly names.
- **Is anything writing that shouldn't be?** Unknown PCs are amber, the first write from one raises a banner, and a
  burst of writes to many files (the ransomware pattern) is flagged and logged.

Also: Maintenance can be changed only from a named PC (closing the accepted risk M8 of the v0.7.0 test plan). And
this release is the "before" measurement for a planned faster network, so it ships first (see Dependencies).

Scope stays ops health. The server can't see a client's own link or disk, so "not the server" is as far as it goes.

## Decisions

Decided by the owner on 2026-11-11; numbered Q1 to Q12 so they don't clash with the cross-repo items (D10 to D14) under Dependencies.

| # | Question | Recommendation |
|---|---|---|
| Q1 | **Where to read the SMB counters.** The fast loop (every second) or the slow sampler. | **Decided: the slow sampler, every 5 seconds** (the fallback). Recommended was the fast loop, but with the SMB categories in it the fast tick measured a 51 ms median against v0.8.0's 43 ms, over its budget. The slow sampler reads the SMB, network and disk counters each pass, so the speeds and the bottleneck are 5-second averages, the burst detector counts each reading's 5 seconds, and the history lines get the average for each of those seconds. The PR reports the slow sampler's own time (`slowMs`) as well as the tick. |
| Q2 | **Link speed and share-to-drive mapping.** The plan named `Get-NetAdapter` and `Get-SmbShare`. | **Decided: neither.** The `Network Interface` counters SRRVRR already reads include each adapter's `Current Bandwidth`, free. `Get-NetAdapter` took about 3 s on the server (module load). Shares map to drives from `Win32_Share`, which SRRVRR already reads with CIM for its share check, avoiding the SmbShare module's load time. |
| Q3 | **How a PC is recognized.** By address, by computer name, or both. | **Decided: by address only.** The server sees a client's address on every session and every page request; names need lookups (cost, latency, and they can be wrong). Named PCs need fixed addresses (D10). A PC with several adapters lists each address. |
| Q4 | **When the bottleneck is named.** | **Decided:** only while the shares move at least 1 MB/s; the resource with the highest percent of its limit is named when it's at or above `BottleneckPercent` (default 80), else "not the server". A new name must come up in two readings in a row before it's shown, so it doesn't flicker. |
| Q5 | **What counts as a write burst.** | **Decided: one PC opening at least `BurstFiles` files (default 500) within `BurstWindowSeconds` (default 60), counting only the seconds in which that PC was also writing.** Loose on purpose: a normal copy of a few hundred photos stays under it, and a program rewriting a share's files goes far over. It ends after `BurstQuietMinutes` (default 5) below the threshold. |
| Q6 | **Burst logging.** | **Decided: the architect's advice as given.** Two `flag` events per burst in the existing event log, `write-burst` when it starts and `write-burst-ended` when it ends, folders and counts only; bursts from one PC closer together than the quiet time are one burst. No separate transfer log: a line per file would hit the 20 MB daily cap within minutes. |
| Q7 | **The unknown-PC banner, "once per PC per session".** | **Decided: once per PC per SMB connection.** A PC that disconnects and reconnects later banners again; the event's key (per PC) means the existing 10-minute repeat rule stops a reconnecting PC from banner-storming. An unknown PC that only reads is amber on the card and logged once per connection, with no banner. |
| Q8 | **What's logged about a PC.** | **Decided:** its friendly name or "unknown", its address and the account it connected as (the point of the flag), folders relative to the share and counts. Never file names. `TransferFolders = $false` drops folders everywhere, leaving counts. **Conflicts with an existing rule:** logs hold no names (v0.7.0, SEC3), and an account is a name. **Decided: the exception, for the four transfer events only** (security flags). Tests and fixtures use plainly fake accounts, and the README says never to paste raw logs or `/events` into a public issue (use `tools\Export-TransferSample.ps1`). |
| Q9 | **Maintenance from a PC that isn't named.** | **Decided: refused (403), and the page shows the checkbox disabled** with "Maintenance can be changed from a named PC. This PC is seen as <its address>." The server itself (loopback and its own addresses) always counts as named. |
| Q10 | **Maintenance when no PCs are named yet.** | **Decided: only at the server itself,** with a startup-log line saying so. Safer than falling back to "anyone", and the release notes tell the owner to add `NamedPCs` before installing. |
| Q11 | **What an unelevated copy shows.** | **Decided: everything the counters give** (the bottleneck, per-share traffic, the share graphs, and write bursts as "a PC (needs administrator)", without folders). The PC list says "PCs and folders need administrator". No unknown-PC events, since it can't tell PCs apart. |
| Q12 | **UAT of the parts that need administrator.** Test builds run unelevated; elevating one is the owner's call (UAC, and it creates the test firewall rules). | **Decided: automated tests carry most of it, with recorded cmdlet output as fixtures; the counter-only parts get an unelevated UAT on the server; and the owner runs one elevated test build for about 15 minutes at the end, for stories 3 and 4 together** (section 9). |

## 1. The Transfers card

A new card, below Storage:
- **The bottleneck line** in plain words: "Bottleneck: the network link, 94% of 1 Gb/s", "Bottleneck: the share's
  drive (its letter), 98% busy, queue 4", "Bottleneck: the CPU, 91%", "Not the server: the client or the path to it", or "Idle". The three
  numbers behind it (link %, the busiest share drive's busy % and queue, CPU %) are always shown in small print.
- **Shares:** one row per share with traffic or open files: name, drive, read and write speed, open files.
- **PCs:** one row per connected PC: friendly name (or its address, in amber, for an unknown PC), account, read
  and write speed, open files, and a "writing" mark. A row expands to its folders: up to 10, each with its share,
  the folder path below the share and the count of open files, those open for writing marked. A PC in a write burst
  is red until the burst ends.
- **A graph** of the shares' total read and write speed, with the same 60 s and 15 min buttons as the others.
- With nothing connected: "No PCs connected to the shares."

## 2. The bottleneck

Every 5 seconds, from the slow sampler's readings (section 6, Q1), as averages over those seconds:

| Resource | Percent of its limit | Shown with it |
|---|---|---|
| The link | The busiest adapter's bytes in or out, as a percent of its `Current Bandwidth` | Speed and link speed |
| The share's drive | `100 - % Idle Time` of the busiest drive behind a share with traffic in the reading (admin shares included) | Busy % and current queue length |
| The CPU | Total CPU %, as on the CPU card | - |

- Below 1 MB/s of total share traffic: "Idle". Otherwise the highest percent is named if it's at or above
  `BottleneckPercent`, else "not the server: the client or the path to it" (Q4). Ties go link, drive, CPU.
- A new name must come up in two readings in a row before it's shown. The raw percents are sent with every reading.
- This is a guide, not proof: a drive at 100% busy with a short queue may still keep up. The numbers are on screen
  so the owner can judge.

## 3. PCs, shares and folders

- **Per share** (counters, every 5 seconds): read, write and total bytes/s; open files; average seconds per request;
  current queue. Instances are the share names. `IPC$` is ignored (no file data); the admin drive shares are kept,
  since they reach the same drives.
- **Per connection** (counters, every 5 seconds): the same numbers per SMB session, by session id. The slow sampler's
  session list (administrator only) turns each session id into a PC: its address, account, SMB version, and
  whether it's signed and encrypted. Several sessions from one address are one PC.
- **Folders** (slow sampler, administrator only): the open files list gives each open file's share, path and
  whether it's open for writing. SRRVRR keeps only the folder (the path without the last part), relative to the
  share, cut to 3 levels and 120 characters, counted per PC. File names are dropped as soon as they're read and
  never stored, sent or logged. With `TransferFolders = $false`, only the counts are kept.
- **Bounds:** at most 64 PCs and 32 shares shown, 10 folders per PC, and 5,000 open files read per sample (beyond
  that, counts only, and the card says "more than 5,000 open files").
- **Named PCs** come from the `NamedPCs` setting only, never from code (Q3). Any other address is unknown.

## 4. Unknown PCs and write bursts

**New event types**, in the event table:

| Type | Severity | Banner | Logged | When | Key |
|---|---|---|---|---|---|
| `unknown-pc` | warn | no | yes | An unknown PC connects to a share (once per connection) | `unknown-pc\|<address>` |
| `unknown-pc-write` | flag | yes | yes | An unknown PC first writes on a connection | `unknown-pc-write\|<address>` |
| `write-burst` | flag | yes | yes | A PC's write burst starts | `write-burst\|<address>\|<start ms>` |
| `write-burst-ended` | flag | no | yes | That burst ends | `write-burst-ended\|<address>\|<start ms>` |

- **Data:** the PC's friendly name or `unknown`, its address and account (Q8). For bursts also the shares, the files
  opened and bytes written so far, up to 5 folders with counts (none with `TransferFolders = $false`), and for the
  end, the duration. Unelevated, a burst's PC is `a PC (needs administrator)` with its session id (Q11).
- **"Writes"** means the connection's write bytes/s counter is above zero, or one of its open files is open for
  writing.
- **The burst detector** keeps, per PC, a 60-slot ring of files opened in seconds when it was writing; it's a pure
  function of the per-second counter readings, so it's tested without a server.
- **Debouncing** is the detector's own quiet time (Q5, Q6). Each burst's events carry its start time in their key,
  so the generic 10-minute repeat rule never drops one half of a pair. A burst still open at a clean stop gets its
  ended event, marked `"reason": "stopped"`.
- **Flags are written past the 20 MB daily cap** (core section 4), and the number of them is bounded: at most one
  pair per PC per quiet time.
- **Maintenance** silences the banners, as for every event; they're still logged, marked.

## 5. Maintenance limited to named PCs

**How the server knows which PC is asking:** the request's remote address (`RemoteEndPoint`, which SRRVRR already
passes to the Maintenance handler and logs), with IPv4-mapped IPv6 addresses turned back into IPv4 and zone ids
dropped, compared with every address in `NamedPCs`. Loopback and the server's own addresses (the Host check's list,
rebuilt once a minute) always match: whoever is at the server is trusted.

- **Order of checks on `POST /maintenance`:** the Host check, then `X-SRRVRR`, `Content-Type` and `Origin` (all
  unchanged), then the named-PC check, then the rate limit. A refusal is 403 with the body
  `{"error":"not a named PC"}`.
- **Refusals are counted, not logged one by one,** in the existing once-a-minute refusal line, which gains the
  addresses refused (up to 5).
- **`/stats` gains `viewer`** (per request): `{ "name": "<friendly name>" or null, "canChangeMaintenance": true }`.
  Computed from the address alone, so it adds nothing measurable.
- **On a PC that isn't named:** the Maintenance state and end time still show; the checkbox is disabled, with the
  message in Q9. On a named PC the header also shows "Viewing from <friendly name>".
- **What's left of the risk:** a device on the local network could claim a named PC's address. That's accepted:
  the page is local-network only, Maintenance only silences banners, and every change is logged with its address.
  M8 in the test plan becomes "narrowed to named PCs", with new test ids.
- **IPv6:** a PC that opens the page by a name that resolves to an IPv6 address is seen by that address. The
  disabled checkbox's message names the address the server saw, so the owner can add it to `NamedPCs` or open the
  page by the PC's IPv4 address.

## 6. Data sources and what they cost

| Source | Where | Needs administrator | Gives |
|---|---|---|---|
| `SMB Server Shares` counters (`ReadCategory`) | Slow sampler, every 5 s | No | Per share: bytes, requests, files opened, open files, queue, seconds per request |
| `SMB Server Sessions` counters | Slow sampler, every 5 s | No | The same per connection, by session id |
| `LogicalDisk` counters `% Idle Time`, `Current Disk Queue Length` | Slow sampler, every 5 s (also read by the fast loop) | No | How busy each drive is |
| `Network Interface` counters, per adapter, with `Current Bandwidth` | Slow sampler, every 5 s (also read by the fast loop) | No | Link use and link speed |
| SMB session list (the `MSFT_SmbSession` CIM class, which `Get-SmbSession` wraps) | Slow sampler | Yes | Session id, client address, account, SMB version, signing, encryption |
| Open files list (`MSFT_SmbOpenFile`, behind `Get-SmbOpenFile`) | Slow sampler | Yes | Session id, share, path, access |
| `Win32_Share` | Slow sampler, every 60 s | No | Share name to path and drive |

- **Cadence in the slow sampler:** sessions and open files every 5 s while any share has traffic or open files,
  every 30 s when idle. The CIM classes are queried directly, not through the SmbShare module, to avoid its load
  time.
- **Unelevated** (a test build): the CIM queries are skipped and the card says "PCs and folders need
  administrator" (Q11). The README's "Administrator vs. not" section gains that line.
- **Errors** (a CIM query failing, a counter category missing) go to the existing sampler-error path: one status
  line and a throttled log line, never a crash. Without the SMB counters the card says so and the rest of SRRVRR
  runs as before.

## 7. Settings

All new, in `SRRVRR.config.example.psd1` with comments and in the README's settings table. Invalid values are one
plain message and exit code 2, as for every setting.

| Setting | Default | Allowed |
|---|---|---|
| `NamedPCs` | `@()` | Up to 32 entries such as `@{ Name = 'Desk PC'; Addresses = @('<its address>') }`. `Name`: 1 to 40 printable characters, unique (case ignored). `Addresses`: 1 to 8 IPv4 or IPv6 addresses each (no ranges, no loopback, unspecified or multicast), unique across all entries. Any other key in an entry is an error, so a typo fails fast. |
| `TransferFolders` | `$true` | `$true` or `$false`; `$false` keeps counts only, on the page and in the log. |
| `BottleneckPercent` | `80` | A whole number from 50 to 99 |
| `BurstFiles` | `500` | A whole number from 50 to 100000 |
| `BurstWindowSeconds` | `60` | A whole number from 10 to 600 |
| `BurstQuietMinutes` | `5` | A whole number from 1 to 60 |

## 8. Contract changes

All additions; nothing is renamed or removed. The `/stats` contract (frozen at 1.0) only grows.
- **`/stats`** gains `transfers`: `available` (bool), `reason` (string or null), `bottleneck` (`name`: `link`,
  `drive`, `cpu`, `none` or `idle`; `percent`; `link`, `drive` and `cpu` with their numbers), `shares` (array) and
  `pcs` (array, each with `name` or null, `address`, `known`, `account`, `smb`, `signed`, `encrypted`, read and
  write bytes/s, `openFiles`, `writing`, `burst`, `folders`), and `updatedMs` (when the slow sampler last read the
  PC list). Plus `viewer` (section 5). Bounded to about 6 KB by section 3's limits.
- **`/history`** gains two lines, `smbRead` and `smbWrite`. An older version loading the saved file ignores lines
  it doesn't know.
- **Events:** the four new types. An older version shows them by type name (its fallback).
- **Settings:** the six above. An older version warns about them and ignores them, so a rollback still starts.
- **`POST /maintenance`** may now answer 403 `not a named PC`.

## 9. Testing, budgets and rollout

**Tests** (ids added to the test plan, sections 6 and 7, which the traceability test checks):
- **Recorded fixtures:** counter readings (`ReadCategory` output for both SMB categories, `LogicalDisk` and
  `Network Interface`) and the CIM classes' output, kept under `tests\fixtures\` as hand-checked data with made-up
  share names and documentation-range addresses. A small tool, run once by the owner during the elevated UAT,
  records real output with names, addresses, accounts and paths replaced, to check the hand-made fixtures' shapes.
- **Pure functions, fully tested:** the bottleneck rule (each resource winning, ties, the idle floor, the 2-second
  hold); the session-to-PC join; folder trimming (file names never survive: a test asserts no fixture file name
  appears anywhere in `/stats` or a log line); the burst detector (start, the window, quiet-time merging, the
  started/ended pair, a stop mid-burst); unknown-PC events once per connection; the named-PC address match
  (IPv4-mapped, zone ids, case, loopback, the server's own addresses); every setting's validation; the bounds.
- **Web:** `viewer` and the 403 for an unnamed address, using the handler's address parameter.
- **The page:** the card's states (idle, each bottleneck, unknown PC, burst, needs administrator) in the existing
  JavaScript tests.

**UAT,** about 15 minutes per PR on a test build:
- **Stories 1 and 2, unelevated, on the server:** copy a large file, then a folder of 600 small files, into a
  scratch folder on the code drive's share through the server's own loopback name (never onto the photo or media
  drives). The bottleneck line and the share rows move; the burst flags and its ended event appear in the Flagged
  list. Optionally run the network test's SMB throughput test as a known load.
- **Stories 3 and 4, elevated, once, by the owner (Q12):** a test build in its own folder on its own port, started
  as administrator. From a named PC, copy a folder to a share: its friendly name, folders and counts show, and
  Maintenance works. From a PC left out of the test config's `NamedPCs`: it's amber, its first write raises one
  banner, and its Maintenance checkbox is disabled with the message. Stop the test build with its own stopper,
  which removes its rules.

**Budgets,** against v0.8.0's baseline (`tools\budgets.psd1`): CPU at most 1% on average; memory at most 25 MB
more; `/stats` p95 at most 30 ms; the page at most 150 ms; startup at most 20 s; the fast tick's median within 10%
(or 5 ms) of v0.8.0's; the slow sampler's own time per pass (`slowMs`) is reported, with no budget. Expected cost: under 1 ms a tick for the counters and the detector; the CIM queries a few
tens of milliseconds every 5 s, only while the shares are busy (measured in story 3, elevated; if they break the
CPU budget, every 10 s); memory a few MB (bounded); `/stats` a few KB more; disk writes only the new events.

**Release and rollout:** the release PR, the tag v0.9.0 and the GitHub release; then the boot launcher's release
that carries it, listing every new file. The release notes tell the owner to add `NamedPCs` to the live config
before installing (Q10). The owner installs it, with an unattended reboot as the finish line.

**Rollback:** reinstall the previous launcher release, which carries v0.8.0. Section 8 is why that works: v0.8.0
ignores the new settings, shows the new events by name, and loads history while ignoring the new lines. Maintenance
goes back to "any device", the accepted v0.7.0 risk. Tried once in UAT.

## Dependencies

Shown to the owner when work starts and before each merge. Install-specific details are in the owner's private
records.
- **D10 (the network project, the owner applies it): fixed addresses for named PCs.** Reservations on the router
  for each PC to be named, one per adapter it uses. Without them a named PC can change address and turn amber, and
  lose Maintenance. Needed before the elevated UAT.
- **D11 (the DNS project): names after its DNS change.** Only needed if PCs are matched by name. With Q3 (addresses
  only) it doesn't block this release; the Host check's names are unaffected.
- **D12 (the shares' permissions work and the network test): the network test's SMB write test.** Once everyday
  accounts can't write to the shares, it needs a test account or share. It's also this release's known load, and
  the card will show the new writer account.
- **D13 (done):** the config is no longer copied from a writable share, so a tampered copy can't mark a PC as named.
- **D14 (ordering): ship v0.9.0 before the faster-network hardware swap,** with a "before" measurement (the network
  test's SMB throughput, with this card's bottleneck line) recorded. If the swap could come first, the owner decides
  whether D14 still holds.
- **The boot launcher** must list every new file in its tamper check, and carries v0.9.0.
- **The project map** records the new `/stats` fields, the new events and the 403, in the same PR as the change.
- **Nothing else changes:** no new ports, firewall rules, accounts or shares. SRRVRR only reads SMB state.

## Not in this release

- A per-file transfer log, or file names anywhere (Q6).
- A reader on the client PCs for their own link and disk (deferred since the first plan).
- Matching PCs by computer name (Q3), and a login for Maintenance (out of v1).
- Blocking or disconnecting anything: SRRVRR watches and reports only.
- Per-share or per-PC thresholds; alerts on throughput.
- Everything planned for v0.10.0 and later: 24-hour history, the phone and a second PC.
